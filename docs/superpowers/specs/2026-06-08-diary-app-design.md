# 日記アプリ 設計ドキュメント

- **作成日**: 2026-06-08
- **対象**: 個人用の Web 日記アプリ（将来的に公開する可能性あり）
- **ステータス**: 技術選定と初期設計の合意済み

## 1. 概要

Web 上で動作する日記アプリを段階的に構築する。最初は1人で使うローカル開発から始め、必要に応じてクラウドへ公開する。

### 1.1 機能要件（最終形）

1. 1日1つの日記を作成できる
2. 日記の履歴を管理・閲覧できる
3. 日記が7日分溜まると、AIが「最近のあなたの考え・気持ちの動向」をまとめてくれる
4. 直近のワンポイントアドバイスをもらえる
5. MBTI に基づく最近の傾向を 4 軸の対立スライダーで可視化できる
   - 当初は「多角形グラフ」を想定していたが、M3 実装後のレビューで
     MBTI の対立軸構造と Radar チャートの設計（独立連続変数を想定）が
     合わないことが明らかになり、対立スライダー形式に変更（2026-06-08）

### 1.2 非機能要件

- ローカル開発で完結する状態から開始する（クラウド契約・課金は当初不要）
- 試作段階では Gemini API の無料枠で AI 機能を賄う
- 将来のマルチユーザー化を見越しつつ、当面はシングルユーザーで動かす
- 試作なので過剰な抽象化・テストは避け、動くものを素早く出す

## 2. 技術スタック

| レイヤー | 採用技術 | 選定理由 |
|---|---|---|
| フレームワーク | Next.js 16 (App Router) | エコシステム最大。Server Actions と Server Components で API ルート不要のシンプル構成が可能 |
| 言語 | TypeScript (strict) | 型安全。Drizzle・Zod と組み合わせて End-to-end の型安全を実現 |
| スタイリング | Tailwind CSS v4 | Next.js 公式デフォルト。学習コスト最小 |
| UI 部品 | shadcn/ui | コピペ式・依存最小・カスタマイズ自由 |
| DB | Neon Postgres (serverless) | 0.5GB + 月191時間の無料枠。Branching が強力で実験しやすい |
| ORM | Drizzle ORM + drizzle-kit | 型安全・軽量・serverless 相性良好 |
| 入力バリデーション | Zod | AI 出力のスキーマ強制にも使う |
| AI SDK | Vercel AI SDK v6 | プロバイダーを抽象化し将来の差し替えを容易にする |
| AI プロバイダー | Google Gemini (`gemini-2.5-flash`) | 無料枠が寛容で個人試作に最適 |
| グラフ | （Tailwind 自前バー） | MBTI 4 軸の対立スライダーで表示。Recharts は使用しない |
| ホスティング | Vercel (Hobby) | 公開する段階で利用。当初はローカル開発のみ |
| Lint/Format | Biome | ESLint + Prettier の後継。設定が簡潔で高速 |
| 認証 | M4 で Better Auth を予定 | 当初はシングルユーザー前提で `DEFAULT_USER_ID` を固定値運用 |

context7 で 2026-06-08 時点の最新情報を確認済み：

- Next.js v16.2.2 が現行安定版。`create-next-app` のデフォルトが App Router + Tailwind + TypeScript + Turbopack
- Vercel AI SDK v6 では `generateObject` が非推奨化され、`generateText` + `Output.object` が新標準
- Drizzle ORM は Neon Postgres serverless 向けの公式チュートリアルあり
- Gemini API は無料枠あり（クレカ登録不要）、`gemini-2.5-flash` が試作に十分な品質

```
│  ┌────────────────┐  ┌──────────────────────┐            │
│  │ Server         │  │ Server Actions       │            │

│  └────────────────┬────────────────────┘                │
│                                                           │
│  ┌─────────────────────────────────────┐                │
│  │ AI Service Layer (Vercel AI SDK)    │                │
│  │  - 週間サマリー生成                  │                │

```

### 3.2 設計の要点

1. **3層に分ける**: 画面（React）、データ操作（Drizzle）、AI 操作（AI SDK）を疎結合に保つ
2. **Server Actions 中心**: 書き込み操作は API ルートではなく Server Actions で表現する
3. **Server Components で読み取り**: 一覧や詳細はサーバーで取得して HTML を返す
4. **AI 処理は別レイヤー**: プロバイダー差し替えに備えて呼び出しを `lib/ai/` に集約する

## 4. データモデル

### 4.1 テーブル定義

```
┌─────────────────────────────────────────────────────────┐
│ diary_entries  (日記本体)                                │
├──────────────┬──────────────────────────────────────────┤
│ id           │ uuid (PK)                                 │
│ user_id      │ text   ← 当面は固定値 "me" 等             │
│ entry_date   │ date   ← 「その日記が何日のものか」       │
│ content      │ text   ← 本文 (Markdown 想定)            │
│ created_at   │ timestamptz                               │
│ updated_at   │ timestamptz                               │
└──────────────┴──────────────────────────────────────────┘
       UNIQUE(user_id, entry_date) ← 「1日1つ」を DB で強制

┌─────────────────────────────────────────────────────────┐
│ weekly_insights  (週ごとの AI 分析結果)                  │
├──────────────────┬──────────────────────────────────────┤
│ id               │ uuid (PK)                             │
│ user_id          │ text                                  │
│ period_start     │ date  ← 集計対象週の月曜              │
│ period_end       │ date  ← 集計対象週の日曜              │
│ summary          │ text  ← 「最近のあなたの動向」まとめ   │
│ advice           │ text  ← ワンポイントアドバイス        │
│ source_entry_ids │ jsonb ← 元になった日記 ID リスト       │
│ model            │ text  ← "gemini-2.5-flash" など       │
│ created_at       │ timestamptz                           │
└──────────────────┴──────────────────────────────────────┘
       UNIQUE(user_id, period_start)

┌─────────────────────────────────────────────────────────┐
│ mbti_snapshots  (MBTI 傾向スコア)                        │
├──────────────────┬──────────────────────────────────────┤
│ id               │ uuid (PK)                             │
│ user_id          │ text                                  │
│ snapshot_date    │ date                                  │
│ scores           │ jsonb ← {ei:0.6, sn:0.3, tf:0.7,...} │
│ source_entry_ids │ jsonb                                 │
│ model            │ text                                  │
│ created_at       │ timestamptz                           │
└──────────────────┴──────────────────────────────────────┘
```

### 4.2 設計の意図

- **`entry_date` で「1日1つ」を強制**: 重複を DB 制約で禁止する。`created_at` と分けることで遡って書く操作も許容する
- **AI 結果を保存する**: 毎回 LLM を呼ぶと遅く、無料枠を消費する。一度生成したら保存する
- **`model` カラムを持つ**: どのモデルで生成したかを記録し、後の検証や再生成判定に使う
- **`source_entry_ids` を持つ**: どの日記から生成された分析かを追跡できるようにする
- **MBTI スコアは `jsonb`**: 軸を増減・差し替えしても DDL 変更が不要
- **`user_id` を先に仕込む**: 認証導入時に UUID へ置き換えるだけで済むよう、最初から列を用意する

### 4.3 YAGNI: 当面入れないもの

| 案 | 理由 |
|---|---|
| `tags` テーブル | 仕様にない |
| `attachments` テーブル | 画像対応は仕様外 |
| `mood` カラム | 気持ちの可視化は AI に任せる |
| `version_history` テーブル | 編集履歴は MVP では不要 |

## 5. 段階的マイルストーン

```
M0 ─→ M1 ─→ M2 ─→ M3 ─→ M4
環境  CRUD  AI    高度な  公開
構築  完成  分析  分析    準備
```

各マイルストーンの終わりで「動く日記アプリ」が手元にある状態を保つ。

### M0: 環境構築（半日〜1日）

**ゴール**: `localhost:3000` で空の Next.js アプリが立ち上がる

- Node.js のインストール（volta または mise でバージョン管理）
- `create-next-app` でプロジェクト雛形作成
- Tailwind CSS, TypeScript, Biome 設定（雛形時に自動）
- Neon プロジェクト作成 → 接続 URL を `.env.local` に貼る
- Drizzle ORM を導入し、`SELECT 1` で DB 接続を確認
- git 初期化 + GitHub にプッシュ（後の自動デプロイ用）

### M1: 日記の基本機能 CRUD（2〜3日）

**ゴール**: 日記を書ける・見返せる。AI なし

- Drizzle で `diary_entries` のスキーマ定義 → `drizzle-kit push` で Neon に反映
- ページ構成
  - `/`: 今日の日記の編集画面（無ければ新規作成、あれば編集）
  - `/history`: 過去の日記一覧（カレンダーまたは日付リスト）
  - `/diary/[date]`: 特定の日の詳細
- フォーム送信 → Server Action で保存
- Zod で入力バリデーション
- 「1日1つ」制約の動作確認

**節目**: ここで実際に何日か日記を書いて、使ってみて分かる改善点を反映してから先に進む

### M2: AI 週間サマリー + ワンポイントアドバイス（2〜3日）

**ゴール**: 過去7日分から「最近のあなた」を AI がまとめる

- `weekly_insights` テーブル追加
- Vercel AI SDK 導入 + Gemini API キー取得
- AI サービス層を `lib/ai/weekly-insight.ts` に実装
  - 7件溜まったらサマリー + アドバイスを生成
  - Zod スキーマで AI の出力形式を強制（`Output.object`）
- `/insights` ページ追加
- 「再生成」ボタン

### M3: MBTI 多角形グラフ（2〜3日）

**ゴール**: 自分の最近の傾向が多角形で見える

- `mbti_snapshots` テーブル追加
- AI 側で MBTI 4軸のスコアリングを実装（プロンプト + Zod スキーマ）
- Recharts の RadarChart で表示
- `/insights` に統合または `/profile` を新設
- 過去のスナップショットを時系列で見られる UI（おまけ）

### M4: 公開準備（必要になったら）

**ゴール**: スマホ等からもアクセスできる

- Vercel に GitHub 連携でデプロイ
- 環境変数を Vercel に登録
- 認証導入（Better Auth）
- ドメイン設定（必要なら）

### 分け方の判断

| 判断 | 理由 |
|---|---|
| M1 で AI を入れない | 基礎を固めてから複雑性を足す |
| M2 と M3 を分ける | プロンプトが別物なので分けたほうがデバッグしやすい |
| 認証を最後に | 1人で使う間は不要。早く入れると開発時のログイン作業が増える |
| デプロイを最後に | ローカル完結の間はクラウド側のトラブルに悩まされない |

### 依存関係のルール

| 層 | 役割 | 依存していい先 |
|---|---|---|
| `app/` | ルーティングと画面 | `components/`, `lib/` |
| `components/` | UI 部品 | 他の `components/` のみ |
| `lib/db/` | DB 操作 | なし |
| `lib/ai/` | AI 呼び出し | `lib/db/` (読み取りのみ) |
| `lib/actions/` | Server Actions | `lib/db/`, `lib/ai/` |

下の層は上の層を知らない。これによりテストしやすさと差し替えやすさを保つ。

## 7. その他考慮事項

### 7.1 環境変数

`.env.example` をリポジトリに含める：

```
# Neon Postgres
DATABASE_URL="postgres://..."

# AI (M2 以降に追加)
GOOGLE_GENERATIVE_AI_API_KEY="..."

# シングルユーザー前提の固定 ID (M4 認証導入時に削除)
DEFAULT_USER_ID="me"
```

実値は `.env.local` に保存し、`.gitignore` で除外する。

### 7.2 エラーハンドリング

- **DB の制約違反**（同日 2 回書こうとした等）: Server Action 内で catch し、ユーザーに分かりやすいメッセージ
- **AI 呼び出し失敗**（無料枠超過、ネットワーク等）: 結果を保存しない。UI に「あとで再生成」ボタンを出す
- **想定外エラー**: そのまま投げて Next.js の `error.tsx` で受け止める

最初から複雑な `error.tsx` は作らず、起きたら都度対応する方針。

### 7.3 テスト

M0〜M1 では書かない。理由：

- 仕様が頻繁に変わる段階で書いてもすぐ書き直しになる
- 個人プロジェクトの試作で時間を取られすぎる
- 「動かして確認」のサイクルが速いため代替になる

M2 以降で書き始めるもの：

- AI 出力のスキーマバリデーション（Zod が自動でやる範囲）
- 「7日溜まったか」のような純粋な計算ロジックには Vitest で簡単なユニットテスト

### 7.4 コード品質ツール

| ツール | 役割 |
|---|---|
| TypeScript (strict) | 型安全 |
| Biome | フォーマッタ + リンタ |
| Drizzle Kit | DB マイグレーション |

## 8. 想定外の調整について

このマイルストーン通りに進めることが目的ではなく、「使ってみて要らない機能は捨て、欲しい機能を足す」前提で進める。例：

- M1 を使って「カレンダー UI より検索が欲しい」となれば、M2 の前に M1.5 として差し込む
- M3 で「やっぱり Big5 のほうがいい」となれば差し替える

## 9. 次のステップ

このドキュメントの合意後、`writing-plans` スキルで **M0（環境構築）** の詳細な実装プランを作成する。M0 完了後に改めて M1 のプランを作成する、というように**マイルストーン単位で実装プランを切る**運用とする。
